## Question and scope

Measure the runtime cost of AddressSanitizer on six public C workloads from
LLVM Test Suite. This transfers the measurement method of the 2012 paper,
Section 4 / Figure 2, to a modern environment and different workloads.
The paper's 73% overhead is contextual evidence, not a target threshold or
a directly comparable result for these programs.

`claim-001`: the paper reports average runtime overhead of 73% on its
SPEC CPU2006 C/C++ subset under its stated configuration. This project
investigates the cost of the same kind of checking on the substitute workloads.
The original numerical claim remains `inconclusive` in this pilot.
No test of bug-detection completeness, physical memory overhead, or official
SPEC scores is part of this experiment.

The user has no licensed CPU2006 package. The public-workload substitution is
accepted by the user; acceptance for course grading has not been confirmed
by the teaching team. This does not block local exploratory preparation.

## Environment and comparison

Reuse the validated Ubuntu / Clang 18 environment. The initial immutable image ID
is in [config/llvm-asan.json](../../config/llvm-asan.json). Record the actual image
ID, kernel, CPU information, packages, compiler versions and cgroup limits per run.
If this image is absent, rebuild through the existing environment procedure,
check it, and record the replacement ID rather than silently downloading an image.

Both arms use Clang 18, `-O2 -g -fno-omit-frame-pointer`; C also uses `-std=gnu89`
because these are legacy C programs. Clear CMake's Release flags so it cannot
silently append `-O3`. The ASan arm additionally uses `-fsanitize=address`
for compilation and linking. No LTO, PGO, source rewriting, or native CPU tuning.

Set the identical process environment for both arms. The baseline ignores ASan
options. The ASan options are explicitly in the configuration: 32-byte minimum
and maximum heap redzones, no quarantine, no allocation stack unwinding, no leak
checking, and no stack-use-after-return checking. Halt on ASan errors with exit
code 86. These approximate selected paper settings; they are not a reconstruction
of the old allocator or compiler. Disabling quarantine changes UAF coverage.
Record the exact options; do not claim they are present-day defaults.

Build first with at most two jobs, then pin execution to the first allowed logical
CPU. Execute one program at a time within the same container. Do not disable host
services, change the power plan, alter CPU governors, change ASLR, or modify WSL.
Other host activity and virtualization can still affect timing.

## Measurement fixed before execution

- One fresh-process warmup per arm and program; warmups are retained but excluded.
- Five fresh-process measurements per arm and program (60 measured samples).
- Within each repetition, run baseline then ASan on odd repetitions, reverse
  on even repetitions. Program order is the table order.
- Use the upstream baseline-built `tools/timeit`, with its exit-status output,
  and baseline-built `tools/fpcmp` against the upstream `.reference_output`.
  Normalize CRLF to LF in comparison copies only; preserve the original output
  and source reference unchanged. No other whitespace is ignored.
- Primary metric: `real` elapsed wall seconds, which includes process startup,
  allocator setup and program output, but excludes compilation and verification.
- Auxiliary metrics: `user` and `sys` seconds. This harness deliberately uses wall
  time rather than the upstream lit default's user-time aggregation.
- Record raw output, timer output, exit status, comparison command and hash for
  every execution, including failed executions.
- Per arm: arithmetic mean and sample standard deviation (`n-1`) over all five
  valid measurements. Ratio = ASan mean / baseline mean; extra time overhead =
  `(ratio - 1) * 100%`.
- Aggregate only if every selected benchmark has all ten valid measurements:
  equal-weight geometric mean of the six runtime ratios. This is a local summary,
  not a claim about the paper's averaging method.
- No outlier removal, result-driven workload resizing, or threshold tuning.
- Flag either arm's mean below 0.05 seconds as too short for strong inference.
  Calibration or repeated-in-process measurements require a new plan/run.

## Resource budget and stopping

- No image pull or package installation during a pilot. Public Git acquisition:
  clone timeout 300 seconds; sparse materialization timeout 180 seconds.
- Container: non-root, no network, read-only root/project/source, no capabilities,
  no new privileges, no core dumps, two CPU quota, 3 GiB RAM, no swap, 128 PIDs,
  and 768 MiB temporary filesystem.
- Configuration per arm: 120 seconds. Build per arm: 300 seconds, two jobs.
- Each program: 60 seconds; timer wrapper grace: five seconds.
- Entire container attempt: at most 1500 seconds, then remove only that run's
  uniquely named container. Require at least 4 GiB available to Docker.
- Stop on source mismatch, missing image, unavailable engine, failed build,
  unsafe isolation, overall timeout, or insufficient resources.
- Preserve a failed run. A retry creates a new run ID.

## Validity and conclusions

Nonzero exit, timeout, sanitizer report, missing timer output, or reference-output
mismatch makes an execution invalid. Missing, invalid or duplicate repetitions
prevent a benchmark ratio and the suite aggregate. Report counts and raw failures.
Such failures are not evidence that ASan is fast or the paper is wrong.

The pilot can establish only whether this pipeline builds, preserves correctness,
and produces usable timing samples. It cannot resolve the original SPEC claim.
Formal confirmation requires a later frozen plan, sufficient durations and an
approved comparison scope. Do not declare support from proximity to 1.73x.

An extension candidate is to change only quarantine size, keeping compiler,
workloads, flags, repetitions and other ASan options fixed. It is not run here.

## Entry points

From the project root on Windows, with Docker Desktop's Linux engine running:

```powershell
python .\scripts\llvm-asan.py fetch
& .\scripts\run-llvm-asan.ps1
```

If the original image has been rebuilt, pass the verified ID with `-Image`.
Source acquisition is independent of Docker. `-FetchOnly` runs only that step.
Each real attempt writes `runs/run-<UTC>-exp-001-a01-<unique>/`.

Validation and analysis:

```powershell
python -m unittest discover -s tests -v
python .\scripts\llvm-asan.py check-source
python .\scripts\llvm-asan.py analyze --output runs/<run-id>
```

Analysis verifies the evidence hashes and writes a new `results/<run-id>/`
without modifying the original run. Preserve that run's effective configuration,
project-source snapshot and source lock even if the project later changes.
